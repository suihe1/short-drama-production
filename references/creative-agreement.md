# 输入、创作范围与用户决策

首次接手素材或任务方向改变时读取。先读用户材料和已有约定，再判断入口；文件后缀、文件名或“短剧”一词都不能代替阅读。区分读过的章节、摘要与尚未覆盖的内容，不声称读完未读取的长篇。

## 按实际任务进入

| 输入 | 合适入口 | 不自动做的事 |
|---|---|---|
| 完整小说 | 根据任务做阅读诊断、角色提取或改编方向方案；需要改编时再进入大纲 | 不默认抽核、合人、删支线；原著扫描不代表全部人物投产 |
| 完整剧本 | 保留原稿，按要求评审、润色、结构化或直接进入导演设计 | 不先重写大纲，不删除已有镜头/表演意图，不把闭环结尾改成悬念 |
| 梗概或不完整剧本 | 标明已有事实与缺口，补足用户要求的部分 | 不把自己的补充伪装成原作事实 |
| 一句话想法 | 提出有差异的方向与推荐理由，再写适合规模的故事提案或样场 | 不在方向未定时铺开整部长剧和全部资产 |
| 已有分镜或成片 | 从指定问题和对应阶段切入，必要时回查上游 | 不为了补齐流程重新编剧 |

输入类型与任务类型分开：完整小说也可能只要求分析；完整剧本也可能明确授权彻底重写。用户的最新明确指令优先于保留原稿的默认策略。

## 先做出可判断的方案

把当前理解简要写在对话或现有项目 notes 中：作品形式（独立短片/连续剧等）、输入覆盖范围、目标、保留点、改动范围和下一份交付。时长、画幅、角色名等能从材料确定的事实直接复用；不要重新问一遍，也不把材料中的旧估时当成用户本轮硬限制。

“看看哪里不好”先给诊断；“润色”默认保持主要事件、关系和结局；“改编”涉及取舍，但没有确定的改编幅度时先给取舍方案；“放开重写”允许在已授权范围内重构，不逐项重复审批。

对会改变主题、核心事件、人物去留、叙事视角或结局的未授权改动，先完成原稿诊断，展示“原位置/原意 → 建议改法或短样段 → 改善什么 → 会损失什么”，给 2–3 个可比较选项并收取用户决定：每项说明具体改法、收益和损失，标出推荐；在适用时包含保留原稿/暂不修改，并允许用户自定义。选项应解决当前真实分歧，不罗列无关偏好。短片通常一份方案即可；长篇或方向分歧明显时才需要多个选项。用户可接受部分、否决部分、指定保留内容或授权模型自行决定某类问题。

只等待依赖该决定的重写；阅读、事实整理、计时和备选样段可以继续。不要先全面重写，再以“需要用户确认”补办方向选择。

## 创作判断与工具约束

模型负责提出有作品针对性的判断：引用具体场次或段落，解释动机、因果、信息、情绪或节奏问题，承认判断的主观性。用户负责目标、取舍和接受程度；不要用“模型更懂”或校验 PASS 替代用户审美。

人物/资产引用、文件完整性、依赖、实际 API 格式和费用授权仍是执行约束。钩子位置、悬念、角色数量、爽点间隔、台词长度、镜头节奏和公式时长通常是项目建议，只有用户或实际交付合同明确要求时才作为创作硬条件。

遇到旧校验器把创作建议判为失败，保留原稿，说明具体限制和适用范围；使用工具已经支持的配置，不编造 JSON 字段、不调参数假装达到实测时长、不把红灯当删戏指令。技术投产预检仍须真实通过。没有 outline/art 时显示未验证，不宣称对账完成。

## 审阅与返工

交付改稿时同时说明保留、增删、结构变化、尚未解决的问题。小改直接给对话差异；长稿提供带场次定位的改稿与简明修改单。先问具体改动是否符合用户意图，避免只问“满意吗”。“再自然一点”先用一段有代表性的样段说明理解；若含义仍影响全稿，再问清楚。

用户接受某段不等于全稿通过；要求修改不等于批准当前稿；开放创作授权不等于付费执行授权。以现有 notes/approvals 记录范围、源版本、用户原意和待决事项，不新增一套审批状态。HTML 只是可选审阅载体，展示和反馈方式见 review-handoff.md。
